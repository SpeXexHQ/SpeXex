# Security Proof and Limits

## ROD Private ECDSA Adaptor Signature v1

**Proof status:** Human-checkable proof argument in the classical random-oracle model. Not machine checked, peer reviewed, or a certificate of production security.

## 1. Exact claim

This document proves functional and proof-system properties of the private adaptor variant specified in `SPECIFICATION.md`. It also gives a conditional transfer argument for a restricted adaptor-unforgeability claim and proves a negative CDH-exposure result.

It does not prove the current wallet implementation satisfies the theorem's input domain. The wallet's permissive point parser demonstrably violates that precondition.

## 3. Model and assumptions

### 3.1 Group

Let `E` be the prime-order subgroup of secp256k1 generated by `G`, with order `n`. All externally supplied points are required to be canonical, non-infinity members of `E`.

### 3.2 Hashes

Tagged SHA-256 invocations are modeled as random oracles on their exact byte domains.

The private variant uses one `DLEQ` tag for the proof nonce and challenge. The two input domains have fixed, disjoint lengths, 163 and 198 bytes, so an input in one role cannot equal an input in the other. This supports modeling the calls as one random oracle queried on domain-disjoint strings. Separate tags would still be cleaner engineering.

Reduction modulo `n` makes the challenge distribution negligibly non-uniform because `n` is slightly below `2^256`. The statistical deviation is at the 128-bit scale and does not reduce the intended security below 128 bits.

### 3.3 Base signature

The base scheme is strict-DER, low-S ECDSA over secp256k1 with 32-byte message digests. The restricted adaptor theorem assumes this profile is strongly existentially unforgeable under chosen-message attack for the relevant key and message domain.

This is an explicit assumption, not a new proof of ECDSA.

### 3.4 Discrete-log proof

The Fiat-Shamir Chaum-Pedersen proof is assumed to operate in the classical random-oracle model. Quantum random-oracle security is not claimed.

### 3.5 Key and protocol restrictions

The theorem requires:

- fresh purpose-specific signing keys;
- no ECDH, ElGamal, or CDH-dependent protocol using the same signing key;
- no invalid or non-canonical point reaches secret-scalar multiplication;
- authenticated binding of `X`, `Y`, the exact message digest, and protocol role;
- no nonce reuse or faulted signing output;
- attestation before a pre-signature is acted upon.

## 4. DLEQ relation

The statement is:

```text
(G, Y, R', R)
```

The witness relation is:

```text
R' = kG and R = kY
```

The prover chooses `w`, commits with:

```text
A1 = wG
A2 = wY
```

and returns:

```text
c = H(G, Y, R', R, A1, A2)
z = w + ck mod n
```

The verifier reconstructs:

```text
A1* = zG - cR'
A2* = zY - cR
```

and checks the hash.

## 5. Lemma: DLEQ completeness

**Claim.** An honestly generated proof always verifies, except negligible encoding-degeneracy events that the algorithm rejects.

**Proof.** Substitute `z = w + ck`, `R' = kG`, and `R = kY`:

```text
A1* = (w + ck)G - c(kG) = wG = A1
A2* = (w + ck)Y - c(kY) = wY = A2
```

The verifier reconstructs the original commitments and therefore computes the same challenge. QED.

## 6. Lemma: DLEQ special soundness

**Claim.** From two accepting transcripts with the same statement and commitments but distinct challenges, one can extract `k`.

Let:

```text
z1 = w + c1*k mod n
z2 = w + c2*k mod n
c1 != c2
```

Subtract:

```text
z1 - z2 = (c1 - c2)k mod n
```

Since `n` is prime and `c1 != c2`, `(c1-c2)` is invertible:

```text
k = (z1-z2) * (c1-c2)^(-1) mod n
```

The executable suite performs this extraction in 128 independently derived cases.

## 7. Lemma: honest-verifier zero knowledge

**Claim.** There is a simulator that produces an accepting transcript without `k` when it can program the random oracle.

Simulator:

1. Choose `c,z` uniformly modulo `n`.
2. Set:

```text
A1 = zG - cR'
A2 = zY - cR
```

3. Program the challenge oracle on `(G,Y,R',R,A1,A2)` to return `c`.

Attestation equations hold by construction. In a real proof, uniform `w` makes `z = w+ck` uniform for fixed `c,k`; therefore the simulated and real transcript distributions agree up to negligible hash-to-scalar bias and rejected degeneracies. QED in the programmable ROM.

The executable suite checks both simulator equations in 128 cases.

## 8. Theorem: private Fiat-Shamir transcript is a DLEQ proof of knowledge

**Claim.** In the classical random-oracle model, a prover that produces an accepting private DLEQ proof with non-negligible probability yields an extractor for `k`, subject to the standard forking-lemma conditions.

**Argument.** Rewind the prover while keeping its internal randomness and all oracle replies fixed until the challenge query for the accepting transcript. Respond with a distinct challenge. Two accepting transcripts with identical commitments and different challenges allow extraction by Section 6.

Prepending the fixed generator and reordering the fixed-length statement fields changes the random-oracle input but not the Sigma protocol, extractor, or simulator. It creates a separate Fiat-Shamir domain; it does not weaken the proof merely because it differs from the DLC encoding.

This theorem does not establish interoperability, quantum-ROM security, or implementation side-channel resistance.

## 9. Lemma: pre-signature equation

The signer computes:

```text
s' = k^(-1)(m + rx) mod n
X = xG
R' = kG
```

Then:

```text
(s')^(-1)(mG + rX)
= (s')^(-1)(m + rx)G
= kG
= R'
```

Therefore an honestly generated pre-signature passes the ECDSA pre-signature equation. QED.

## 10. Theorem: adaptability and completed-signature correctness

Given witness `y` for `Y = yG`, completion computes:

```text
s = s' * y^(-1) mod n
```

ECDSA attestation reconstructs:

```text
s^(-1)(mG + rX)
= y(s')^(-1)(mG + rX)
= yR'
= y(kG)
= kY
= R
```

By definition, `r = x_coordinate(R) mod n`, so `(r,s)` is a valid ECDSA signature.

If low-S normalization replaces `s` with `n-s`, attestation reconstructs `-R`. The points `R` and `-R` have the same x-coordinate, so ECDSA remains valid. QED.

## 11. Theorem: witness extraction and uniqueness

Without low-S negation:

```text
s' * s^(-1)
= s' * (s' y^(-1))^(-1)
= y mod n
```

If completion emitted `n-s`, extraction first obtains `n-y`. The algorithm tests both candidates against `Y` and returns the one whose scalar multiple of `G` equals `Y`.

Uniqueness follows because `G` has prime odd order `n`. If both `yG = Y` and `(-y)G = Y`, then `2yG = O`; this implies `y = 0 mod n`, excluded by the witness range. QED.

The implementation MUST also require the completed signature's `r` to match the pre-signature's `R`; otherwise extraction may be attempted from an unrelated signature with a coincidentally useful `s`.

## 12. Negative theorem: public CDH exposure

**Claim.** A valid ECDSA adaptor pre-signature reveals the Diffie-Hellman point `xY` to anyone who knows the public transcript.

The public values satisfy:

```text
R = kY
s' = k^(-1)(m + rx)
```

Compute only with public scalar and point operations:

```text
D = r^(-1)(s'R - mY)
```

Substitute:

```text
s'R
= k^(-1)(m + rx)(kY)
= (m + rx)Y
```

Therefore:

```text
D
= r^(-1)((m + rx)Y - mY)
= r^(-1)(rxY)
= xY
```

No discrete logarithm is required. The vector suite computes `D` and independently computes `xY` from test secrets for all 16 vectors; every pair matches.

### Consequence

The scheme cannot satisfy a broad opacity or simulation claim saying a pre-signature reveals no useful information beyond an encrypted signature. It is unsafe when the signing key participates in ECDH, ElGamal, or any protocol whose security assumes `xY` is hidden.

This is a property of the practical ECDSA adaptor construction, not a consequence of the private DLEQ transcript. It is documented in Fournier's analysis and the `secp256k1-zkp` API warning.

The party holding `y` can already compute the same point as `yX`; the additional exposure is to observers who know only the public transcript and to other protocols that reuse `x`.

## 13. Negative result: unlinkability

The pre-signature contains `R`, while the completed ECDSA signature contains:

```text
r = x_coordinate(R) mod n
```

Anyone holding the pre-signature can link it to the completed signature by comparing `r`, subject only to the rare x-coordinate reduction ambiguity. The scheme is not unlinkable.

The OTC protocol may still hide the pre-signature from passive chain observers, but plaintext relay publication, logs, or later disclosure removes that privacy.

## 14. Restricted adaptor-unforgeability theorem

The 2026 work *Practical Adaptor Signatures: Security and Applications* reports a proof for the deployed practical ECDSA adaptor construction under a relaxed security definition and strong unforgeability of ECDSA. Earlier broad definitions do not faithfully capture this ECDSA construction.

The private variant changes the DLEQ proof's Fiat-Shamir encoding and deterministic proof nonce, but not:

- the relation being proved;
- the pre-signature equation;
- completion;
- extraction; or
- the public CDH exposure.

Sections 5 through 8 establish the completeness, extraction, and simulation properties needed from the replacement DLEQ proof in the classical ROM. Therefore the modern practical-ECDSA argument can be transferred **conditionally**, provided its theorem requires only these NIZK properties and all assumptions in Section 3 hold.

This document deliberately does not reproduce or claim a complete peer-reviewed reduction for the 2026 definition. The currently available paper abstract states the theorem, but this experiment has not machine-checked every game hop against the authors' final formalism.

The supported conclusion is:

> The private transcript does not introduce an evident proof-system flaw and is reducible to the same DLEQ relation. Restricted adaptor security is plausible and conditionally inherited; broad adaptor security is not proven and some broad properties are false.

## 15. Adversarial viewpoints

### 15.1 Malicious adaptor-point owner

A malicious peer chooses `Y`. Under strict validation, `Y` remains in the prime-order group and cannot trigger invalid-curve multiplication. Without strict validation, the proof does not apply and the wallet can multiply secrets by off-curve points.

### 15.2 Malicious signer

A malicious signer can send arbitrary pre-signatures. DLEQ and the pre-signature equation prevent acceptance unless the object is consistent with a nonce witness and the named signing key/message, under the proof-of-knowledge and ECDSA assumptions.

### 15.3 Public relay observer

An observer learns all plaintext transcript data, can link a disclosed pre-signature to its final signature, and can compute `xY`. The observer should not learn `x` or `y` under the intended hardness assumptions, but no witness-hiding reduction is supplied here.

### 15.4 Fault attacker

Nonce reuse or faulted scalar multiplication can defeat the mathematical model. A signer SHOULD self-verify every pre-signature before release, use hardened constant-time arithmetic, and prevent faulted or partially corrupted output.

### 15.5 Cross-protocol attacker

The format has no version byte and uses generic `DLEQ` tagging. A protocol using the same signing keys or transcript conventions can create unintended composition. Purpose-specific hardened keys and versioned domain tags are required.

### 15.6 Related-key attacker

ECDSA admits algebraic related-key/message transformations outside the ordinary single-key EUF-CMA model. The OTC terms must authenticate the exact public key and transaction digest, and chain-specific signing children should be used.

### 15.7 Quantum attacker

No post-quantum security is claimed. Shor's algorithm breaks the discrete-log assumptions; quantum random-oracle Fiat-Shamir analysis is also outside scope.

## 16. Proof obligations not discharged

The following would be required for a stronger formal claim:

1. A machine-checked model of the group and serialization layer.
2. A complete game-based reduction against the exact 2026 relaxed definition.
3. A proof for deterministic nonce derivation under an explicit PRF/ROM model.
4. A multi-user, related-key, and cross-chain composition theorem.
5. A protocol model covering both blockchains, reorganization, observation, refunds, and message reordering.
6. Constant-time and fault-resistance evidence for the implementation.
7. A proof that every deployed parser enforces the theorem's canonical input domain.

## 17. Research interpretation

The literature progression matters:

- Fournier identified the ECDSA construction's CDH exposure.
- Fournier's original appendix explicitly marks its attempted broad ECDSA reduction as wrong, so this experiment does not rely on that reduction.
- Aumayr et al. formalized adaptor signatures for generalized channels.
- Dai et al. identified shortcomings and strengthened definitions.
- Gerhart et al. showed further gaps affecting practical compositions.
- Hubacek, Maskova, and Richterova introduced a relaxed notion intended to capture practical ECDSA adaptor signatures and reported a proof under strong ECDSA unforgeability.

A statement that this protocol is simply "proven secure" would ignore those model changes. The defensible claim is property-by-property and assumption-by-assumption, as recorded above.
